# Consejo independiente — 0liviA

Fecha: 2026-10-04
Estado: **propuesta + slice vertical local verificado**

## Resumen ejecutivo

La arquitectura más fuerte para el límite de 2 OCPU / 12 GB ARM64 no es apilar un workspace, un harness, una base vectorial y un framework de voz completos. Recomiendo un **control plane pequeño propio**, con interfaces estables y procesos efímeros:

- **API/UI:** servidor ASGI pequeño (la prueba actual usa únicamente la biblioteca estándar) con streaming SSE/WebSocket y una sesión por usuario.
- **Estado durable:** SQLite + archivos Git versionados para decisiones, checkpoints y memoria promovida; sin vector DB como dependencia inicial.
- **Router:** interfaz OpenAI-compatible propia con políticas de timeout, presupuesto, fallback y circuit breaker; ningún proveedor gratuito es parte de la verdad del sistema.
- **Trabajo largo:** jobs persistidos, cada uno con branch/worktree, eventos, checkpoint y reanudación idempotente.
- **Herramientas:** allow-list de herramientas MCP/GitHub, modo read-only por defecto y elevación explícita para mutaciones.
- **Voz:** WebRTC programable (LiveKit self-host como primera candidata) separado del control plane; VAD barato local, STT streaming CPU, LLM por el router y TTS streaming intercambiable.

El repositorio estaba vacío de código ejecutable. Añadí la menor prueba que demuestra `browser → sesión → router → SQLite → estado de repo → SSE` sin afirmar que ya exista una voz o un LLM de producción.

## Decisión principal y runner-up

### Principal: control plane pequeño + adaptadores, no un framework monolítico

La prueba vertical ya demuestra que se puede mantener una superficie reemplazable sin depender de SaaS. LiveKit Agents es la mejor **candidata de voz**, no el núcleo completo: su documentación oficial describe participantes realtime programables, clientes WebRTC, turn detection semántico, MCP, pruebas y self-hosting. Aun así, el objetivo de USD 0 exige medir el servidor y los workers en el A1 real antes de adoptarlo.

### Runner-up: LiveKit Agents como runtime de voz y un harness coding externo

Es razonable si la velocidad de llegar a voz supera el coste de operar otro proceso. No lo convierto en decisión aún porque el footprint ARM64, la latencia española y la operación de TURN/STUN no están medidos en la VM objetivo. Agent Zero, Letta Code, Tenet, OmO y HarnessRouter siguen siendo referencias/candidatos: ninguno fue aceptado solo por README o popularidad.

## Evidencia verificada

- LiveKit Agents: el README oficial declara integraciones intercambiables STT/LLM/TTS, clientes WebRTC, turn detection semántico, MCP, framework de tests y stack self-hostable. Fuente: https://github.com/livekit/agents/blob/main/README.md (consultada 2026-10-04).
- Moonshine Voice: el README oficial declara procesamiento on-device, streaming de baja latencia, bindings para Python/JS-WASM/Linux/Raspberry Pi y licencia MIT con excepciones explícitas para modelos legacy no ingleses. Fuente: https://github.com/moonshine-ai/moonshine/blob/main/README.md (consultada 2026-10-04). La calidad y latencia en español sobre ARM64 siguen **NO VERIFICADAS localmente**.
- Silero VAD: el README oficial reporta modelo JIT de aproximadamente 2 MB, menos de 1 ms por chunk de 30+ ms en un hilo CPU, opción ONNX y licencia MIT. También documenta que sus ejemplos Python listan requisitos x86-64/AVX; para ARM64 se debe probar el camino ONNX y no extrapolar el benchmark. Fuente: https://github.com/snakers4/silero-vad/blob/master/README.md (consultada 2026-10-04).
- Kokoro: el README oficial declara 82M parámetros, pesos Apache y pipeline con español (`lang_code='e'`). El primer audio, RAM y velocidad en A1 ARM64 siguen **NO VERIFICADOS**. Fuente: https://github.com/hexgrad/kokoro/blob/main/README.md (consultada 2026-10-04).
- GitHub MCP Server: el README oficial documenta `--read-only`, allow-list por toolsets/tools, PAT por entorno y prácticas de mínimo privilegio. Lockdown mode es un filtro best-effort de contenido y no una frontera de autorización. Fuente: https://github.com/github/github-mcp-server/blob/main/README.md (consultada 2026-10-04).
- GhostCall: el repositorio existente solo tiene evidencia pública de UX/WebRTC; no hay API/SDK/programmatic bot contract verificado. Se mantiene como referencia de UX, no como dependencia.

## Memoria y contexto

1. **Working state:** solo en el evento/job actual.
2. **Conversación:** `messages(session_id, role, content, created_at)` en SQLite.
3. **Checkpoint:** documento Git con estado, último evento, branch/worktree, comandos y siguiente acción.
4. **Memoria durable:** hechos promovidos explícitamente, con `source`, timestamp, confianza y proyecto/sesión.
5. **Decisiones:** ADR append-only en Git.
6. **Episodios:** resumen de tarea con resultado, fallos, retries y evidencia.
7. **Skills:** procedimientos versionados, no texto libre auto-promovido.
8. **Conocimiento de repo:** índices derivados reconstruibles; source-of-truth sigue siendo el repo.

Reglas: no guardar cada turno; promover solo preferencias/facts repetidos o confirmados; contradicciones crean una nueva versión; el retrieval debe devolver fuente y fecha; compaction conserva objetivos, restricciones, decisiones, errores y siguiente acción.

## Routing

Contrato mínimo: `complete(messages, tools, deadline, policy) -> stream(events)`. Cada adapter debe exponer latencia, coste/quota, errores y cancelación. El router:

- clasifica simple/coding/research/voice;
- intenta el proveedor permitido más barato/rápido;
- limita tokens, tiempo y tool calls;
- aplica retry solo a errores transitorios;
- abre circuit breaker ante rate limits/fallos;
- hace fallback sin duplicar mutaciones;
- registra modelo/provider/latencia, nunca secrets ni chain-of-thought.

Los proveedores gratuitos cambian o caducan: el sistema debe continuar con degradación a texto/fallback local, no tratar una cuota como disponibilidad garantizada.

## Voz propuesta

`browser mic → WebRTC → VAD → streaming STT → misma session_id → router LLM → streaming TTS → browser audio`.

- Transporte inicial a probar: LiveKit self-host; alternativa mínima: WebSocket/WebRTC directo si el media server consume demasiado.
- VAD: Silero ONNX o VAD del runtime, medido en A1.
- STT: Moonshine primero por su enfoque streaming/on-device; faster-whisper como baseline de precisión, no como supuesto de realtime.
- TTS: Kokoro como baseline español; MOSS-TTS-Nano como experimento alternativo CPU. Ninguno se declara aceptado hasta TTFA/RAM reales.
- Barge-in: un `turn_id` cancelable; el navegador detiene audio inmediatamente y el backend cancela STT/LLM/TTS asociados.
- Fallback: si voz falla, conservar transcript y continuar en texto con la misma session_id.

GhostCall no es elegible como backend programático mientras no exista un contrato público verificable.

## Seguridad

- Secretos solo en variables/secret store; nunca en Git, memoria, logs o prompts persistentes.
- Herramientas read-only por defecto; mutaciones de GitHub, deploy, delete y publicación requieren autorización explícita.
- Branch/worktree aislado para trabajo; no ejecutar instrucciones de repos/web sin tratarlas como contenido no confiable.
- GitHub MCP con `--read-only` y toolsets allow-listed para discovery; token por proyecto, mínimo privilegio y rotación.
- Timeouts, límites de salida, sandbox de shell, auditoría de eventos y rollback por commit.

## Envelope objetivo (estimación, no medición)

| Componente | Objetivo inicial |
|---|---:|
| Control plane Python | <150 MB RSS idle |
| SQLite + archivos | <1 GB, excluyendo repos grandes |
| Web UI | estática, sin proceso adicional |
| VAD/STT/TTS | procesos on-demand, límites explícitos |
| LiveKit server | medir por separado; no aceptar sin prueba A1 |
| Jobs coding | uno activo por defecto en 2 OCPU |

La única evidencia local obtenida aquí es la prueba estándar; **no** se ejecutó una VM Oracle A1 y **no** se deben interpretar estas cifras como benchmark.

## Matriz de benchmark antes de congelar

- API: TTFT, TTFA, p50/p95, cancelación, reconnect, errores y consumo.
- Voz: microphone-ready, partial transcript, endpoint, primera ficha LLM, TTFA, barge-in, español, 30/60 min, CPU/RAM.
- Coding: comprensión de repo, bug fix, feature multiarchivo, tests fallidos, browser QA, resume, provider failure; éxito, retries, wall time y regresión.
- Memoria: recall exacto, contradicción, supersession, restart, separación de proyectos, precisión de retrieval y tamaño de contexto.
- Infra: cold boot, restart recovery, backup/restore, disco, RAM y migración a VM limpia.

## Lo realmente implementado

- `prototype/server.py`: HTTP API sin dependencias externas; SQLite durable; router fallback determinista; `git status` read-only; SSE tokenizado; session endpoint; límites básicos.
- `prototype/static/index.html`: UI browser mínima con session ID persistente en localStorage y consumo SSE.
- `prototype/test_server.py`: dos pruebas de health/streaming y persistencia de contexto entre requests.

## Verificado / no verificado

**VERIFICADO:** compilación Python; dos pruebas unitarias pasan; health endpoint; sesión SQLite; streaming SSE; estado de repo read-only; ausencia de dependencia de Cloudflare/servicio pago en el slice.

**NO VERIFICADO:** proveedor LLM real; WebRTC; voz; STT/TTS; ARM64 Oracle; carga/concurrencia; autenticación multiusuario; sandbox de shell; backups remotos; despliegue; GhostCall programático.

## Riesgos y siguiente acción exacta

1. Medir en una A1 real el control plane y un único worker de voz, empezando por Silero ONNX + Moonshine + Kokoro.
2. Añadir un adapter OpenAI-compatible con timeout/cancelación y pruebas usando servidor falso local; nunca activar credenciales en tests.
3. Reemplazar SSE por WebSocket para eventos bidireccionales de voz, manteniendo el contrato de sesión.
4. Añadir jobs/checkpoints y una política de aprobación para mutaciones.
5. Repetir benchmarks con transcriptos españoles y conservar resultados en `docs/RESEARCH.md`.

Este informe no afirma producción ni despliegue. Su objetivo es dejar una arquitectura falsable y un primer camino ejecutable.
