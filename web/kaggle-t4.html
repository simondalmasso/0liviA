Dos T4 pueden evaluar un modelo. No son el servidor de 0liviA.

Decisión técnica basada en las dos propuestas de Sakana, el repositorio actual y la documentación oficial de Kaggle. Separamos el laboratorio efímero del Core permanente y mantenemos el objetivo de coste recurrente cero sin inventar disponibilidad ni resultados.

NO-GO: Kaggle no se utiliza como API persistente, endpoint tunelizado, heartbeat, worker de GitHub Actions ni proveedor del router. Uso propuesto: benchmark privado, manual, acotado y offline con datos sintéticos, sin conversaciones ni secretos.

La arquitectura aprobada

Core permanente

0liviA

Identidad, sesiones, memoria SQLite, jobs, checkpoints, router y coding worker siguen independientes de Kaggle. El Core no recibe tráfico desde notebooks.

Laboratorio efímero

Kaggle T4×2

Notebook privado para compilar llama.cpp, cargar GGUF desde un dataset privado, ejecutar pruebas sintéticas y exportar métricas. Sin servidor HTTP ni túneles.

La AUP vigente enumera expresamente “server farming” y actividad no relacionada con ML/data science entre los usos abusivos de recursos. Los Terms limitan el servicio a uso propio, interno, personal y no comercial. Por prudencia, no publicamos ni automatizamos un servicio de inferencia desde Kaggle.

Los puntajes publicados por los fabricantes son resultados de sus propios harnesses y no predicen el rendimiento de 0liviA en T4. El número de parámetros activos de un MoE no equivale al tamaño de sus pesos residentes.

Memoria y runtime

  • Las dos T4 no comparten una única VRAM: pesos, KV cache y buffers deben caber en cada tarjeta.
  • Primera opción: llama.cpp + GGUF, compilado para CUDA SM 7.5.
  • Distribución inicial: layer con split equilibrado; muestrear VRAM de ambas GPU cada 2 s mientras corre cada proceso (los picos más breves pueden no capturarse).
  • Herramientas: llama-bench y llama-cli. No se inicia llama-server.
  • Contexto escalonado: 8K → 16K → 32K. 64K sólo si la medición deja margen.
  • Los archivos de pesos se adjuntan como dataset privado: el disco auto-guardado documentado es 20 GB y el GGUF principal puede superar ese tamaño.

Son umbrales de ingeniería propuestos, no resultados observados. Todo resultado debe incluir SHA del modelo, cuantización, runtime, driver, contexto, split, throughput prefill/decode, wall time y muestras de VRAM por GPU. La plantilla no mide TTFT exacto ni un soak de 20 llamadas; ambos siguen siendo gates separados. Evalúa funciones sintéticas de un solo archivo, no cambios multiarchivo.

Plan de ejecución

  1. Confirmar cuota real en el panel de Kaggle y mantener el notebook privado.
  2. Adjuntar un dataset privado con GGUF y manifest de origen, licencia y SHA-256.
  3. Validar dos T4 y compilar el commit fijado de llama.cpp.
  4. Medir Qwen3.6 y luego Qwen3-Coder con los mismos prompts sintéticos.
  5. Exportar metrics.json, revisar calidad fuera de Kaggle y documentar resultados.
  6. Integrar un proveedor sólo si existe otra infraestructura autorizada con coste cero verificado; Kaggle no entra al router.

La notebook separa stdout/stderr, incluye throughput de llama-bench y muestras de VRAM en metrics.json. El código generado pasa por una política AST y un subprocess con límites; es defensa en profundidad para el fixture, no un sandbox general.

Estado actual: no ejecutado No se inició sesión GPU, no se cargó ningún modelo, no se midió velocidad ni se desplegó producción.
